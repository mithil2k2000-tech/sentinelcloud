# Security Posture Dashboard

The last portfolio-checklist item. Named without a roadmap phase number, same reason as Compliance Mapping/Attack Simulation/Architecture Diagrams above (see `claude/roadmap.md`'s numbering note).

## What this is

`agent/dashboard.py` reads the JSON reports every other CLI in this project already produces — `analyze.py`'s three per-cloud threat-model reports, `k8s_scan.py`'s manifest-gate report, `report_compliance.py`'s audit-style report, `drift_scan.py`'s demo report, `detect.py`'s demo report, `attack_sim.py`'s two chain reports (naive and hardened), and `agent/eval/benchmark.py`'s harness result — and renders them onto one self-contained HTML page and one plain-text summary. Ten separate CLIs become one page someone can open and read in ten seconds, instead of running each tool by hand to answer "what does this project's security posture actually look like right now."

## What this deliberately is not

**Not live monitoring.** Every number on the dashboard was read from a JSON file an earlier CLI run already wrote to `threat-model/` or `kubernetes/manifests/`. `dashboard.py` never calls a cloud API, never polls anything, and never refreshes itself — it's a snapshot renderer, and the page says so, with a generation timestamp, in a banner at the top rather than in fine print. This project has never had a real cloud account to monitor in the first place (cost discipline, §14/§20 of the spec) — calling this a live dashboard would be a plain overclaim, the same category of mistake SR-6's reference-only compliance labeling exists to prevent, applied here even though no compliance framework is involved.

**Not a new source of judgment.** `dashboard.py` computes nothing — every ALLOWED/BLOCKED, every severity count, every PASS/FAIL, every feasibility label on the page is copied verbatim from a report some other, already-tested engine produced. If a number on the dashboard is wrong, the bug is in whichever engine generated the underlying report, not in this rendering layer — `tests/test_dashboard.py` checks the page against the real committed report files exactly for this reason, not against any new logic (there isn't any to be right or wrong about).

**Not a gate.** Like `report_compliance.py`/`attack_sim.py` before it, the CLI always exits 0.

## What's on the page

Seven sections, one per underlying report: the three per-cloud threat-model gates (deployment decision + severity counts), the Kubernetes manifest gate, the compliance audit report (with its reference-only label carried through unconditionally), the attack-path simulation (naive proposal vs. hardened baseline), the drift-detection demo, the detection-engine demo, and the agent evaluation harness's pass rate. A missing report degrades gracefully — the section reads "no report found" rather than crashing the whole page, since not every environment will have regenerated every report.

## Honest limitations

- **Only as fresh as the last time each underlying CLI ran.** If a report file goes stale relative to the code that produced it (e.g. someone changes a rule but doesn't re-run `analyze.py`), the dashboard will confidently show the old number — there's no hash-check or re-run trigger built in.
- **No historical view.** Every render is a single point-in-time snapshot; there's no trend line, no "this got worse since last week." Adding one would need a real datastore, which is out of scope for a project whose whole design center is $0/local/simulated.
- **CI posts the plain-text summary to the job summary, not the HTML page.** GitHub Actions job summaries render Markdown, not arbitrary HTML with embedded `<style>`, so the rich page is uploaded as a downloadable artifact instead (same pattern as every other report in this pipeline) while the job summary gets the compact text table.

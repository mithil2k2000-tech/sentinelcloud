# Compliance/audit reporting polish (spec §16 table item 8)

Status: **built, tested, and run for real**. 15 new tests (221 total in
`tests/`, all passing: 14 in `test_report_compliance.py`, 1 more in
`test_compliance.py` for the shared `control_ids_in_source` utility).

## What the spec asks for, verbatim

> **Objective:** Turn Phase 5's mapping into a rendered audit-style
> report.
> **Key files:** `agent/report_compliance.py`
> **Tests required before "done":** Snapshot test of report output
> against a fixed architecture.

"Phase 5" here is the spec's own §16 table numbering (compliance mapping,
FR-8 — see the numbering note at the top of `claude/roadmap.md` for why
this doc doesn't try to map that onto the roadmap's own, different phase
numbers). This module does not add any new finding logic of its own — it
is a rendering layer over two things that already exist:
`threat_engine.py`'s deterministic rules, and
`policy/framework-mappings.yaml`'s control-to-framework data.

## What was built

**`agent/report_compliance.py`** — takes one `architecture.json`, runs it
through `threat_engine.run_engine()` exactly as `analyze.py` does, then
renders a per-framework PASS/FAIL checklist: every control
`threat_engine.py` could possibly touch gets one row, PASS if no finding
referenced its `control_id` this run, FAIL (with the actual finding(s)
listed) if one did. Three sections, one table each — CIS Controls v8,
NIST CSF 2.0, PCI DSS v4.0 — followed by a "failing controls" detail
section. Every report unconditionally carries `compliance.py`'s
`REFERENCE_ONLY_LABEL` in its title line.

```
$ python3 report_compliance.py ../threat-model/architecture-hardened.json --as-of 2026-09-18
# Compliance Audit-Style Report (reference only, not a certification)
...
## Executive summary
- Controls in scope: 6
- PASS: 4
- FAIL: 2
```

CLI flags: `--json out.json` (the same rows, structured), `--out
report.md` (write the rendered report to a file instead of stdout),
`--as-of LABEL` (stamps the report; defaults to "not specified" rather
than today's date — see "Why there's no default timestamp" below).

## Why this is scoped to 6 of the 15 mapped controls, not all 15

This is the one design decision worth explaining, because getting it
wrong would have produced a genuinely misleading report. `policy/
framework-mappings.yaml` has 15 entries as of Phase 7 (drift detection):
6 from `threat_engine.py`, 8 from `k8s_engine.py`, 1 (`DRIFT-001`) from
`drift.py`. A naive version of this report would walk all 15 and mark
anything with no finding this run as PASS — but `report_compliance.py`
only ever runs `threat_engine.py` against one `architecture.json`. It
never touches a Kubernetes manifest or a drift snapshot, so it has no way
to know whether `K8S-003` or `DRIFT-001` actually hold — marking them
PASS would be claiming an assessment that never happened, exactly the
kind of overclaim SR-6 exists to prevent.

The fix: `compliance.control_ids_in_source(threat_engine.py)` — a small,
reusable regex-scan utility, extracted from the exact technique
`tests/test_compliance.py`'s static-scan tests already used and proven —
computes the real 6-control surface `threat_engine.py` can emit, and only
those 6 ever appear as a row. `K8S-*`/`DRIFT-*` controls don't show up as
PASS, FAIL, or anything else in this report; they're simply out of scope,
and the report says so explicitly in its own "Scope" line. (A Kubernetes-
or drift-specific version of this same report is a natural extension —
see "Next steps" — but doesn't exist yet, and this report doesn't
pretend to cover that ground in the meantime.)

## Why there's no default timestamp

`render_audit_report()` takes `as_of` as an explicit, optional string
that defaults to `None` (rendered as "not specified") rather than calling
`datetime.now()` internally. This is what makes the snapshot test
possible at all: if the render function silently stamped today's date,
the exact same inputs would produce different output on every run, and
"snapshot test of report output against a fixed architecture" would be
untestable as a byte-exact comparison. The CLI (`report_compliance.py`'s
`main()`) is free to pass a real date via `--as-of "$(date -u
+%Y-%m-%d)"` — and the CI job does exactly that — but the rendering
function itself stays pure.

## The required test, run for real

`threat-model/audit-report-hardened.md` is a real, committed artifact —
generated by actually running `report_compliance.py` against
`architecture-hardened.json` with `--as-of 2026-09-18`, not hand-typed.
`test_render_audit_report_matches_committed_snapshot` in
`tests/test_report_compliance.py` re-renders the same report from the
same fixture and asserts byte-for-byte equality against that file. A
second test does the same thing through the CLI's `--out` flag, so both
the pure rendering function and the actual command a person would run are
covered. Fourteen more tests cover the scoping decision above, PASS/FAIL
determination, sorting, grouping multiple findings under one control,
determinism across repeated calls, and the always-exit-0 guarantee below.

## Why this always exits 0, even when controls fail

`report_compliance.py` is a report generator, not a second gate.
`threat-model-gate` (via `analyze.py --fail-on HIGH`) already makes the
real BLOCKED/ALLOWED call on the exact same findings this report reads —
duplicating that decision here, with a second, possibly different
threshold, would create two sources of truth for the same question. So
this CLI always returns 0 regardless of how many controls FAIL; the
report's job is to make the existing decision legible in an audit-style
format, never to make a second, competing one. The hardened Azure
baseline's 2 FAIL rows (`IAM-004`, `NET-003` — the same `NET-WAF-01`/
RR-05 and `IAM-BROAD-02`/RR-06 findings already tracked in
`threat-model/residual-risk-register.md`) are visible in the report and
in CI's job summary either way — nothing is hidden, the threshold just
isn't re-applied here.

## CI integration

Added an eighth job, `compliance-audit-report` (non-gating, `needs:
unit-tests`), which renders the report against the hardened Azure
baseline with today's date and posts the Markdown straight into the job
summary (GitHub renders it natively, unlike the plain-text `tee`d output
the other demo jobs use) — see `docs/ci-cd.md` for the full eight-job
breakdown.

## Honest limitations

- **Azure-only, single-architecture, by design of this first cut.** The
  CLI takes exactly one `architecture.json` — running it three times (one
  per cloud) and stitching the results into one cross-cloud report is a
  natural next step, not built here.
- **No Kubernetes or drift equivalent yet.** As explained above, this
  report is deliberately scoped to what `threat_engine.py` alone can
  assess. A `report_compliance.py --engine k8s` (or a separate module)
  that does the same PASS/FAIL walk against `k8s_engine.py`'s 8 controls,
  and similarly for `drift.py`'s, would need its own in-scope-control
  derivation and its own committed snapshot fixture — real, additional
  work, not a trivial parameter change, given each engine's control
  surface and finding shape differ slightly in how they're invoked.
- **PASS means "no finding this run," not "verified compliant."** A
  control reading PASS here means `threat_engine.py` didn't flag it for
  this specific architecture on this specific run — it is not an
  independent verification that the control is actually implemented
  correctly, only that this project's own deterministic rule for it
  didn't fire. This is the same caveat every other `--compliance` output
  in this project carries, restated here because an audit-style report's
  whole visual language (a checklist with PASS/FAIL) invites reading more
  confidence into it than a plain finding list would.

## Running it yourself

```bash
cd agent
python3 report_compliance.py ../threat-model/architecture-hardened.json --as-of 2026-09-18
python3 -m pytest ../tests/test_report_compliance.py -v
```

## Next steps for this piece

1. A cross-cloud version that runs all three hardened architectures and
   renders one combined report, rather than one CLI invocation per cloud.
2. A Kubernetes-engine and a drift-engine equivalent of this same
   PASS/FAIL-checklist format, each scoped to its own engine's real
   control surface the same way this one is scoped to `threat_engine.py`'s.
3. An HTML or PDF rendering option for an actual audit deliverable a
   non-technical stakeholder could read without a terminal — today this
   only produces Markdown/JSON.
